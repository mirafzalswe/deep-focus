# Блокировка сайтов через PAC в настройках прокси текущего пользователя

## Контекст

Бриф требует блокировать домены в браузерах (R72) и предлагал расширение Chrome (R70). Классический способ — файл hosts — требует прав администратора. Пользователь прямо сказал: без прав администратора и «расширения для браузера пока не нужно».

## Решение

Блокировка работает через системный прокси текущего пользователя с PAC-файлом. Приложение пишет в HKCU только свою строку автоконфигурации и поднимает на 127.0.0.1 локальный сервер, который отдаёт PAC и служит заглушкой для заблокированных доменов: на HTTP показывает страницу «Заблокировано», на HTTPS отвечает отказом. Остальной трафик идёт мимо приложения. Блокируется домен целиком, вместе с поддоменами.

## Почему

- **Файл hosts** отвергнут: нужны права администратора, пользователь отказался. Он же дал бы блокировку «для всех программ» без согласия пользователя на уровне системы, а откат после сбоя пришлось бы делать с повышенными правами.
- **Расширение браузера** отвергнуто: пользователь отказался. Оно единственное умеет блокировать часть сайта (YouTube Shorts), но требует установки в каждый браузер и защищённого канала команд с приложением (R142). Этот выигрыш мы сознательно не получаем.
- **PAC в HKCU** подошёл, потому что пишется без повышения прав, действует во всех браузерах и программах, следующих системному прокси, и при падении сервера браузеры сами идут напрямую, то есть интернет не ломается.

## Последствия

- Блокировать можно только домен целиком; блокировка отдельных страниц и разделов (Shorts) невозможна. Вместе с доменом закрываются его поддомены и входы через него на других сайтах.
- Выбрать отдельные браузеры нельзя. Программа или браузер со своим прокси блокировку обходят.
- Уже открытые вкладки работают до перезагрузки страницы.
- Если у пользователя свой PAC (корпоративный), блокировка недоступна: чужую настройку не трогаем. Свой обычный прокси сохраняется и продолжает работать для остальных сайтов.
- Мы меняем пользовательские настройки Windows, поэтому обязаны сохранять исходные значения и возвращать их при выключении, выходе, сбое и удалении приложения. Это требует деинсталлятора с флагом очистки и починки «хвоста» при запуске.
- «Блокировка включена» нельзя утверждать по факту записи в реестр: после включения приходится проверять, что система действительно резолвит заблокированный адрес на заглушку. Иначе статус честно «ошибка».
- Применение настроек требует уведомления WinINET через одноразовый вызов PowerShell, то есть зависимость от PowerShell.
