# Раскладка «файлы по доменам» для параллельной сборки

## Контекст

Проект собирается восемью задачами, часть которых идёт параллельно (бриф задаёт порядок: виджет, таймер, блокировка, звуки, задачи, аналитика). Исполнители не видят чужих изменений в процессе работы.

## Решение

Первая задача создаёт каркас всех модулей с заглушками, общие файлы типов, каналов и значений по умолчанию целиком. Дальше каждая задача пишет только в папки своего домена: модуль в main, свой файл в preload, свой словарь, свои страницы и тесты. Точка входа main только вызывает регистрацию модулей и не меняется. Общие файлы позже получают только добавления полей, без переименований. Имена в файле интерфейсов обязательны для всех.

## Почему

- **Последовательные задачи** отвергнуты: сборка шла бы заметно дольше, хотя большая часть доменов независима.
- **Общие точки правки** (одна точка входа, один словарь, один файл preload, который дописывают все) отвергнуты: параллельные правки одного файла приводят к конфликтам слияния и к тому, что два исполнителя называют одно поле по-разному.
- Раскладка по доменам превращает конфликт в вопрос договорённости, который решается заранее в файле интерфейсов.

## Последствия

- Первая задача обязана заранее знать форму всех доменов; ошибка в ней дороже любой другой. На практике это случалось: часть методов системного прокси пришлось сделать асинхронными вопреки исходной подписи.
- Не вся работа делится по доменам: жизненный цикл (трей, выход, закрытие окон) пересекает всех и остался исключением — одна задача правит точку входа, и ей пришлось дорабатывать чужие решения (временные горячие клавиши виджета, прямое уведомление блокировщика).
- Любая новая сквозная функция сначала требует договорённости об общих типах.
- Словари разбиты по доменам, поэтому проверка полноты русского и английского текстов держится на типах, а не на просмотре.
