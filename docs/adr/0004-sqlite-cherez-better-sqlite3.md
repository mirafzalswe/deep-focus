# Локальная база: SQLite через better-sqlite3

## Контекст

Бриф (R132, R135) требует локальную SQLite для настроек, задач, истории, пресетов, правил и состояния восстановления. Нативный модуль в Electron может не собраться на машине без Visual Studio, поэтому в спецификации был запасной вариант.

## Решение

Данные хранятся в SQLite через better-sqlite3 в процессе main, в режиме WAL, с миграциями, которые только дописываются в конец. На практике модуль подхватывается готовой сборкой (prebuild) и грузится и в Node, и в Electron без пересборки. Повреждённый файл базы переименовывается, создаётся новая база, пользователь получает сообщение.

## Почему

- **sql.js (SQLite в WASM)** отвергнут как основной вариант: база живёт в памяти, и каждое сохранение означает запись всего файла целиком через временный файл и переименование. Для строки восстановления, которая пишется каждые 15 секунд и на каждом переходе таймера, это дороже и рискованнее при сбое во время записи. Оставался запасным, если нативная сборка окажется невозможной; не понадобился.
- **better-sqlite3** подошёл: синхронный API без промисов в коротких обработчиках main, запись устойчива к сбоям благодаря WAL.

## Последствия

- Зависимость от наличия готового бинарника под версию Electron: версии зафиксированы точно, `npmRebuild` выключен, потому что на машине сборки нет Visual Studio. Обновление Electron или модуля может сломать это, пока не выйдет подходящий prebuild.
- Схему менять только миграциями вперёд; откатов нет.
- Драйвер скрыт за слоем хранилища, так что при необходимости замена (например, на sql.js) затрагивает только его, но данные между движками придётся переносить.
